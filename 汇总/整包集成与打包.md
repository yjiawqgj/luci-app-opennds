# 整包集成与打包 · 编译 `.apk` / `.ipk` 前的最后一块

> 本文档不属于任何单个页面，是**把 9 个页面拼成一个可编译的 OpenWrt 软件包**所需的全部约定。
> 前面 9 份页面文档各写各的页面逻辑，本文统一定死：文件树、菜单结构、ACL、依赖、安装脚本、首次使用引导。
> **冲突时以本文的路径与包名为准**——页面文档里若有出入，是实现遗漏，不是本文错了。

---

## 1. 包标识

| 项 | 值（写死，不许改） |
|---|---|
| 包名 `PKG_NAME` | `luci-app-opennds-cpd` |
| 版本 | `1.0.0`，`PKG_RELEASE:=1` |
| 架构 | `all`（纯脚本 + JS，无二进制） |
| 显示名 | `LuCI support for openNDS Captive Portal` |
| 目录 | `feeds/luci/applications/luci-app-opennds-cpd/` |
| 后端脚本 | `/usr/lib/opennds/opennds-cpd-api.sh`（全包**唯一**一个） |
| 分发脚本 | `/usr/lib/opennds/theme_zone_detect.sh`（themespec，由区域识别页写进 openNDS 配置） |

> `.apk` 和 `.ipk` **不需要写两套 Makefile**。同一个 Makefile 在 OpenWrt 24.10 SDK 下产出 `.ipk`，
> 在 25.x / snapshot SDK 下产出 `.apk`，格式由 SDK 决定。唯一要改的是 CI 里 `opkg install` 与
> `apk add` 的命令区别，包本身不用动。

> **openNDS 版本基线**：本套文档里所有涉及 openNDS 内部行为的结论（`libopennds.sh` 的
> `preemptivemac()` / `auth_restore()` / `create_client_ruleset()`、nft 表族 `ip nds_filter`
> 与 `ip nds_mangle`、`sh/get_client_interface.sh` 的输出格式）都是按**项目里那份 `sh/`
> 快照对应的版本**（10.x 世代）核对出来的。升级到 11.0.0 时这三处会变，实现里凡是直接写
> nft 命令或依赖脚本行为的地方都要按目标版本再核一遍：
>
> | 差异点 | 本套文档（10.x 快照） | 11.0.0 |
> |---|---|---|
> | nft 表族 | `ip nds_filter` / `ip nds_mangle` / `ip nds_nat` | `inet nds_filter` / `inet nds_mangle` / `inet nds_nat` |
> | `preemptivemac` 的定时刷新 | 主进程调 `preemptivemac quiet`，而脚本只判 `[ -z "$1" ]`，`quiet` 被当成一个 MAC 名 → **名单不会被重读**，必须由插件自己调一次不带参数的 `libopennds.sh preemptivemac`（见 §11.2、各页「应用」语义） | 脚本已认 `quiet`（ChangeLog: *Preemptivemac not taking config values*），主进程每轮自动重读 |
> | 配置键 `ndsctlsocket` | `ndsctlsocket` | 改名 `ndsctl_sock` |
>
> 所以：**别把 `nft list chain ip nds_filter …` 这类命令当成跨版本通用**——冒烟脚本里要按
> 目标机的表族取（先 `nft list tables` 看有没有 `inet nds_filter`，没有再退回 `ip nds_filter`）。

## 4. ACL（`usr/share/rpcd/acl.d/luci-app-opennds-cpd.json`）

```json
{
  "luci-app-opennds-cpd": {
    "description": "Grant access to openNDS captive portal configuration",
    "read": {
      "ubus": { "file": [ "read", "stat", "list" ] },
      "uci": [ "opennds", "zone_blacklist", "zone_detect" ],
      "file": {
        "/usr/lib/opennds/opennds-cpd-api.sh": [ "exec" ],
        "/usr/lib/opennds/zone_markers": [ "read" ],
        "/usr/lib/opennds/cpd/": [ "read", "list" ],
        "/etc/config/opennds": [ "read" ],
        "/etc/config/zone_blacklist": [ "read" ],
        "/etc/config/zone_detect": [ "read" ]
      }
    },
    "write": {
      "ubus": { "file": [ "write", "exec" ] },
      "uci": [ "opennds", "zone_blacklist", "zone_detect" ],
      "file": {
        "/usr/lib/opennds/opennds-cpd-api.sh": [ "exec" ],
        "/usr/lib/opennds/zone_markers": [ "write" ],
        "/usr/lib/opennds/cpd/": [ "write", "list" ],
        "/etc/config/opennds": [ "write" ],
        "/etc/config/zone_blacklist": [ "write" ],
        "/etc/config/zone_detect": [ "write" ],
        "/tmp/zone_up/": [ "write", "list" ]
      }
    }
  }
}
```

要点：

- `file` 段是 rpcd `file` 插件按**路径前缀**判权限，末尾带 `/` 表示允许该目录下任意文件。
  `/usr/lib/opennds/cpd/` 这一条同时覆盖了 `wireless/`、`wired/`、`blacklist/`、`default/` 四棵树。
- `exec` 权限必须写**脚本完整路径**（不能写目录），否则 `fs.exec()` 会返回 `Permission denied`。
  上面 read / write 两段都写了同一条 `exec`，因为 `fs.exec` 走的是 ubus `file` 对象的方法调用，
  ACL 匹配在 write 段；只写 read 段时部分固件会拒绝，两段都写最稳。
- `uci` 只列三个配置：`opennds`（原生）、`zone_blacklist`、`zone_detect`。**不要**图省事写 `["*"]`，
  那等于给这个包改全系统配置的权限，过不了 LuCI 社区的包审核。
- 全局锁 `/var/lock/opennds-cpd.lock` 由 `opennds-cpd-api.sh` **在脚本内部**用 `flock` 持有，
  脚本经 `fs.exec` 以 root 身份运行，不需要为锁文件单独开 ACL 条目。
- 装包后**必须实测**一次：`ubus call file exec '{"command":"/usr/lib/opennds/opennds-cpd-api.sh","params":["overview","status"]}'`，
  返回 JSON 才算 ACL 配对。

## 5. 依赖

```makefile
LUCI_DEPENDS:=+luci-base +rpcd-mod-file +opennds +flock +iw
```

| 依赖 | 为什么 |
|---|---|
| `luci-base` | 前端框架，所有 `view/*.js` 都 `require luci.*` |
| `rpcd-mod-file` | `fs.exec` / `fs.read` / `fs.write` / `fs.list` 全靠它，漏了整包按钮全废 |
| `opennds` | 被管理对象，且 `ndsctl` 由它提供 |
| `flock` | **不是 busybox 默认 applet**，OpenWrt 标准固件里 `flock` 命令通常不存在。整包的写操作互斥全靠它（§11.3 一把锁），漏装的表现是每个 apply 都 `flock: not found`、锁形同虚设、并发写坏 `/etc/config/opennds`。必须写进硬依赖 |
| `iw` | 无线区域识别与客户端接入点反查全靠它：`get_client_interface.sh` 用 `iw dev <if> station dump` 把无线客户端从 `br-lan` 精确到 `phyN-apM`，分发脚本用 `iw dev` / `iw dev <if> info` 判类型、读 SSID。**漏了它不会报错，只会让所有无线客户端被当成有线**——区域门户整片失效、全部落到有线类型默认门户，日志里只有一行 debug。必须写进硬依赖 |

**可选依赖不要写进 `LUCI_DEPENDS`**：
`dnsmasq-full`（Walled Garden 自动模式、访问限制页的「自动阻止」才需要；OpenWrt 22.03 及更早
还要 `ipset`）——写进硬依赖会导致默认装 `dnsmasq` 的固件
装不上本包。改为在两页各自做运行时探测，缺了就在页面上提示（《WalledGarden.md》决策 #12、
《访问限制.md》决策 #15 已定义）。

`rpcd-mod-file` 在 24.10 是默认预装的，但仍要写进依赖：用户可能刷了精简固件。

## 6. conffiles 与出厂模板

两个自建配置文件属于用户配置，**升级包时必须保留**：

```makefile
define Package/$(PKG_NAME)/conffiles
/etc/config/zone_blacklist
/etc/config/zone_detect
endef
```

`root/etc/config/zone_blacklist`（出厂内容）：

```
config main 'main'
	option portal ''
	list mac ''
```

`root/etc/config/zone_detect`（出厂内容）：

```
config zone_detect 'main'
	option session_scope 'default'
```

> `zone_detect` 只预置 `session_scope`（会话管理页的"默认/覆盖"，缺了按 `default` 读也行，
> 写上是为了 uci 里看得见）。**不要预置 `option scope`**：区域识别页用"已保存值"判断
> 用户到底选过模式没有，出厂就写 `scope=global` 会让新装机器一进页面就看到"已保存：全局"，
> 与"首次进入无从判断、显示无"的语义冲突。

> 注意 `list mac ''` 是一条空串条目，读的时候要过滤掉（`uci -q get zone_blacklist.main.mac`
> 会把空行也吐出来）。**写入必须按 §11.2 走 `added` / `removed` 差集，禁止整体替换**——
> 概览页拉黑和黑名单页编辑会交替写这个文件，谁整体重写谁就会把对方刚写的条目冲掉；
> 只有接口层收到显式 `clear=1` 时才允许 `delete` 整个 list（黑名单页 UI 不产生这个参数，见《客户端黑名单.md》§5）。

**不要**把 `/etc/config/opennds` 写成 conffile——那是 opennds 包自己的文件，两个包同时声明会打架。

## 7. postinst / prerm

`Makefile` 里：

```makefile
define Package/$(PKG_NAME)/postinst
#!/bin/sh
[ -n "$${IPKG_INSTROOT}" ] || {
	chmod 755 /usr/lib/opennds/opennds-cpd-api.sh
	chmod 755 /usr/lib/opennds/theme_zone_detect.sh
	mkdir -p /usr/lib/opennds/cpd/wireless /usr/lib/opennds/cpd/wired /usr/lib/opennds/cpd/blacklist
	rm -f /tmp/luci-indexcache
	rm -rf /tmp/luci-modulecache
}
exit 0
endef
```

要点：

- `chmod 755` 那两行**不能省**。opkg/apk 装包时不一定保留 git 里的可执行位，而 themespec
  不可执行 → openNDS `source` 失败 → 所有客户端弹不出门户，且日志里只有一行含糊的报错。
- `mkdir -p` 只建三个业务目录，**不建 `cpd/default/*`**（类型默认门户目录由设置页在用户
  首次上传默认门户时创建）。分发脚本只按 `[ -f ]` 判文件、不看目录，这里只是维持"目录按需建"
  这一条约定（原因见 §2 的提示）。
- 清 LuCI 缓存这两行是必须的，否则装完菜单要等缓存过期才出现，用户以为装失败。
- `[ -n "$${IPKG_INSTROOT}" ]` 是离线构建（`opkg install --root`）保护，不能改。
- **postinst 绝对不要动 `/etc/config/opennds`**。用户可能已经在用别的 themespec 或 FAS，
  装个插件就把人家的登录方式改掉是不可接受的。引导放在 UI 层（见 §9）。

`prerm` 不做任何事，不删配置、不删门户文件：

```makefile
define Package/$(PKG_NAME)/prerm
#!/bin/sh
exit 0
endef
```

> ⚠️ **这条有意为之，但要在文档里说清代价**：卸载后 `/etc/config/opennds` 里仍然是
> `login_option_enabled='3'` + `themespec_path='/usr/lib/opennds/theme_zone_detect.sh'`，
> 而脚本已经被删掉——openNDS 会 source 一个不存在的文件，客户端弹不出门户（日志里是
> `generate_splash_sequence: not found` 一类）。所以**卸载前应先到「区域识别」页切回
> 「默认模式」再点应用**（那一步会把 `login_option_enabled` 写回 `1`）。
> 不在 prerm 里自动改，是因为 prerm 在升级时也会跑（opkg 升级 = prerm → 解包 → postinst），
> 自动改配置会让"升级"顺手把用户的登录模式打回默认。

## 9. 首次使用引导（装在包里必须做，否则用户以为坏了）

装完包、还没进过区域识别页时，`themespec_path` 是空的，openNDS 用自带页面。
此时插件 9 个页面**都能打开、都能配置，但门户完全不生效**——这是最容易收到的"装了没用"投诉。

约定：

1. **区域识别页顶部检测**：`status` 返回 `engaged` 字段，判定条件
   `login_option_enabled=='3' && themespec_path=='/usr/lib/opennds/theme_zone_detect.sh'`。

## 11. 跨页统一约定（运行时）

### 11.1 停用状态下点「应用」

openNDS 的 `enabled` 是**全局运行开关**。init 脚本（`/etc/init.d/opennds`）的 `start_service()`
不读它，真正读的是主程序 `conf.c`：`enabled != 1` 就打印 "openNDS is disabled" 然后 `exit(0)`。
所以 `enabled=0` 时 `/etc/init.d/opennds restart` 的真实表现是——procd 拉起进程 → 进程读配置
→ 立刻退出 → **脚本仍返回 0**，而 `pidof opennds` 永远拿不到。

结论：**只看 restart 返回码会假报成功，只等 `pidof` 会白等到超时。** 所有会写
`/etc/config/opennds` 的页面，apply 必须按下面顺序处理：

1. 先读 `uci -q get opennds.@opennds[0].enabled`，**空值按 `1`**（官方默认启用）。
2. 为 `0` 时先弹二次确认，文案固定：

   > openNDS 当前处于停用状态。继续应用将同时启用它并重启服务：所有设备会短暂断线，
   > 未认证的设备将被重新挡在门户外。确定继续？

   - **取消** → 整单中止，一个字都不写；
   - **确认** → 照常写配置 + `uci set opennds.@opennds[0].enabled='1'` + `uci commit opennds`
     + `/etc/init.d/opennds restart`。

   前端得先知道当前是不是停用态才弹得出这个框：**所有会写 `opennds` 的页面，它的只读接口
   （`status`；会话页是 `get`）必须一并返回 `"enabled":0|1`**（键缺失按 `1`）。确认后重发
   同一个写接口时带 `confirm_enable=1`（各页的写接口名不一样：区域识别 / 设置 / 会话 / 路由器 /
   WalledGarden / 访问限制 是 `apply`，**豁免页是 `save`**，黑名单页是 `save_macs`；概览页不适用，见下面的适用范围表）。
   后端读到 `enabled=0` 而没收到这个参数，**不写任何东西**，
   直接返回 `{"ok":0,"error":"need_confirm","enabled":0}`（与 `duplicate` 同一种用法，见 §12）——
   防的是绕过前端直接调接口，把停用态悄悄改掉。
   前端给写接口拼 `confirm_enable` 时，统一作为**最后一个参数**传 `confirm_enable=1`；后端在各页解析业务参数之前先扫一遍 argv，把这一项摘出来（有 = 已确认，摘掉后剩下的才是该页文档列的位置参数）。**各页 API 表不重复列这个键**，统一按本节追加。
3. 响应里带 `"enabled_by_apply": 1`（**各页 API 表的返回示例不再重复列这个键，
   统一按本节追加**；不返回它，前端那条「openNDS 已同时启用」的 warn toast 就永远不会出现）。
   前端成功 toast **照该页演示原文不变**
   （本包各页分别是「配置已应用」/「应用成功」/「配置应用完成」等，别统一改写），
   因为这次顺手把服务启用了，再追加一条 warn toast「openNDS 已同时启用」——只在 `enabled_by_apply=1` 时出现，平时没有。
4. **apply 流程只许把 `enabled` 写成 `1`**（这是"顺手启用"，见上一条）。写 `0`（停用）**只能**来自概览页的启停开关——那是唯一的停用入口，其它页面的任何按钮都不得写 `0`。
5. 重启后仍要轮询就绪，不能靠返回码判定成功：后端以「`pidof opennds` 有值 **且** `ndsctl status` 能成功」为就绪判据，**最多 15 秒**（30 次 × 0.5 秒）——只看 `pidof` 会把"刚拉起来就因配置错误退出"当成成功，也不能拿 `pidof` 冒充服务健康（进程在、socket 还没起来时 `ndsctl` 会失败）。概览页前端再轮询 `run_state` 等到 **20 秒**，两处都超时才报失败。

适用范围：

| 页面 | 是否适用 |
|---|---|
| 区域识别 / OpenNDS设置 / 客户端会话管理 / 路由器访问 / WalledGarden / 访问限制 | **适用**（apply 必然 restart） |
| 客户端豁免管理 | **适用**，但只在「开关值发生变化」而需要 restart 时判断；只增删名单不重启，不必问 |
| 客户端黑名单 | **适用**。`save_macs` 本次**确实新增了名单条目**（真的拉黑）才重启 openNDS，停用态下拉黑等于没拉，必须先弹确认；只删除（解除拉黑）、只改门户选择、`add` 里全是已在名单里的 MAC（什么都没写进去）都不重启，不需要确认 |
| OpenNDS概览 | 不适用。它自己的开关就是全局启停；停用时列表已清空、行内按钮禁用，编辑弹窗打不开 |

### 11.2 名单写入：按 MAC 增删，禁止整体覆盖

插件里被多页读写的名单有 `opennds.trustedmac`、`opennds.preemptivemac` 和 `zone_blacklist.main.mac`。
多个页面都会动它们，所以写入接口统一按**差异**处理，不按**快照**处理：

1. 写接口收两个集合：**新增集合**与**删除集合**，**不收"最终名单"**。参数名各页按自己的
   语义定（黑名单页 `add` / `remove`，豁免页 `trusted_add` / `trusted_remove` /
   `preempt_add` / `preempt_remove`，概览页是单 MAC 操作），本节只管语义、不管参数拼写。
   后端读当前 uci → 只对新增集合追加、只对删除集合删除 → **其它条目一字不动**。
2. **删除按 MAC 匹配整条**，不按条目原文。前端手里的条目原文可能已经过期
   （别的页面改过参数），按原文匹配会删不掉，用户看到的是"点了删除没反应"。
   同一 MAC 由后端保证只存一条。
3. **禁止 `uci delete` 整个 list 再重写**。唯一例外是显式 `clear=1`（接口层显式清空：
   黑名单页 `save_macs` 的 `clear`、豁免页 `save` 的 `preempt_clear`），
   它连并发新增的一起清掉——这是"清空"本身的语义。
   **单写者的 list 不受这条限制**：`preauthenticated_users`（WalledGarden 页）、
   `walledgarden_fqdn_list` / `walledgarden_port_list`（同页）、`users_to_router`（路由器访问页）、
   `blocklist_fqdn_list` / `blocklist_port_list`（访问限制页）
   全插件只有一个页面写，允许「delete 整个 list → 逐条 `add_list`」整份重写——
   《WalledGarden.md》§5.6 与《路由器访问.md》§5.6 就是这么写的。
   判断标准只有一条：**会不会被第二个页面写**。会 → 必须按差集；不会 → 可以整份重写。
   `preauthenticated_users` 只有 WalledGarden 页写、没有第二个写者，所以整份重写是安全的；
   一旦以后有别的页面也要加 Walled Garden 规则，就必须改成差集，否则两边互相清。
   **第三种情况：`authenticated_users`**——本页只认领 `block` 条目，但 block 必须排在
   别人的 `allow` / `passthrough` 前面（《访问限制.md》决策 #14），`add_list` 又只能往后追加，
   所以只能整份重建。重建前必须 `uci -q get` 把原有条目完整读出来，非 block 条目
   **按原顺序原样写回**，一个都不许丢、不许换位；这不是"清空"语义，别当成例外来扩大使用。
4. **每条数据只归一个页面写**：

   | 数据 | 唯一写入者 | 其它页面 |
   |---|---|---|
   | `preemptivemac` 条目的 5 个参数 | 概览页编辑弹窗（5 项）、会话管理页「覆盖」（把 `sessiontimeout` 改 `0`；条目缺别的字段就补 `0`，**已有的其它 4 个参数原样保留**） | 其它页面只读；增删条目时原样保留 |
   | `preemptivemac` / `trustedmac` 的成员 | 豁免页（批量增删）、概览页（单点增删）、**黑名单页（拉黑时摘除，只删不增）** | 都按 MAC 增删；黑名单页那条删得掉，靠的正是"删除按 MAC 匹配整条"，所以它也必须读当前 uci 再删，不许拿前端旧列表当准 |
   | `zone_blacklist` 的成员 | 黑名单页（批量）、概览页（单点） | 都按 MAC 增删 |
   | 会话超时的**全局值** | 会话管理页 | — |
   | 各条目的 `sessiontimeout` 置 0 | 会话管理页「覆盖」 | 已有的其它 4 个参数一律不动（缺的补 `0`，见《客户端会话管理.md》§3） |
   | `authenticated_users` 里的 **`block` 条目** | 访问限制页（整份重建：新 block 在前、原有条目按原顺序跟在后面） | 同一 list 里的 `allow` / `passthrough` 条目**不归任何页面**，谁都不许删改；访问限制页读写时一律原样保留（《访问限制.md》§5.6、另见《访问限制.md》§5.7）。`block` 必须排在 list **最前面**——`create_client_ruleset()` 先把整份 list 倒序、再逐条 `insert … index 2`，链内顺序 = list 顺序，排在 `allow all` 后面就永远命不中 |
   | `blocklist_fqdn_list` / `blocklist_port_list` | 访问限制页 | 无第二个写者（WalledGarden 写的是 `walledgarden_*` 那一对，别搞混） |

5. 概览页「免认证」是唯一"新增带参条目"的单点操作：写一条 6 参数写全的条目
   （五个参数全写 `0`，openNDS 里 0 = 跟随全局/默认值；缺字段反而会继承上一条
   客户端的值，见《OpenNDS概览.md》§3.2）；
   若该 MAC 已在名单内，**不覆盖已有参数**，**按成功返回**（`{"ok":1,…}`，不报错）——
   这种情况只会出现在"别的页面刚把它加进去"的竞态里，报错会让用户以为这次操作失败；
   同页的按钮状态在下一次轮询后自然会变成「移除免认证」。

6. **`trustedmac` 与 `preemptivemac` 必须互斥**（同一个 MAC 只能在一个名单里）：
   - 批量写入（豁免页 `save`）先按本次增删算出应用后的两个集合，**取交集，非空整单拒绝**，
     返回 `{"ok":0,"error":"duplicate","duplicates":["aa:bb:cc:dd:ee:ff"]}`，uci 一个字节不动，由用户删掉一边再应用；
   - 单点写入（概览页设「可信任」）意图明确，后端**自动把该 MAC 从 `preemptivemac` 摘掉**；
   - 任何写入路径都不许留下交集。openNDS 里 `trustedmac` 的规则优先，交集不会导致断网，
     但会让用户搞不清这台设备到底算哪一类、计不计流量，所以必须在插件层拦住。

**这条约定的效果**：谁后写都不会冲掉别人写的东西，除非两个人改的是同一个 MAC 的同一个字段。

### 11.3 跨页面互斥：应用前抢锁，抢不到就返回「忙」

概览页的倒计时遮罩（《OpenNDS概览.md》§3.1）只管住**当前这一个页面**。用户开两个标签页，
或者一个标签页在概览页拉黑、另一个在 WalledGarden 点「应用」时，两个后端进程仍会同时
写配置并重启——后果是后起的进程刚建好 nft 链，前一个的 `service_stopped()` 醒来执行
`delete_chains` 把它删掉，门户放行规则整片消失。

所以**所有会写 `/etc/config/opennds`、`/etc/config/zone_blacklist`、分发脚本运行时要读的
门户文件（`cpd/` 下任意文件、`zone_markers`），或者要重启服务的接口**，入口第一步统一抢锁：

```sh
command -v flock >/dev/null 2>&1 || {
    printf '{"ok":0,"error":"系统缺少 flock 命令，请先安装 flock 包"}\n'
    exit 1
}
exec 9>/var/lock/opennds-cpd.lock
if ! flock -n 9; then
    printf '{"ok":0,"busy":1,"page":"%s"}\n' "$PAGE"
    exit 0
fi
printf '%s %s %s\n' "$$" "$(date +%s)" "$PAGE" > /var/run/opennds-cpd.busy
trap 'rm -f /var/run/opennds-cpd.busy' EXIT
```

规则：

1. **一把锁**：`/var/lock/opennds-cpd.lock`，所有页面共用，不按文件拆（拆了就要处理
   多把锁的获取顺序，写反一处就死锁；写配置本身只有毫秒级，拆锁没有收益）。
   锁命令本身要先验存在：`flock` 不是 busybox 默认 applet，缺包时**必须直接报错退出**，
   绝不允许"没有 flock 就照常写"——那样等于没有互斥，两个页面同时 apply 会把配置写坏。
2. **非阻塞**：用 `flock -n`（不是 `-w`）。抢不到**立刻返回** `{"ok":0,"busy":1}`，
   让用户自己重试，不让他在页面上干等。
3. **状态文件只用于展示，不用于互斥**：`/var/run/opennds-cpd.busy` 里是
   `pid 起始时间 页面名`，用来告诉前端"上一步是什么、跑了多久"。互斥**只认 flock**——
   进程崩了 fd 关闭、锁自动释放，而状态文件可能残留，不能拿它当锁。
   所以 `status` 里的 `busy` **不读状态文件**，用「试抢即放」现算：
   `exec 9>/var/lock/opennds-cpd.lock; if flock -n 9; then flock -u 9; busy=0; else busy=1; fi`。
   （**各页 `status` 的返回示例不重复列这个键，统一按本节追加**——漏了它，页头那条
   「另一个页面正在应用」的提示条永远不会出现。）
   否则进程被 `kill -9`（`trap` 跑不到）时状态文件残留，页头会永久挂着一条
   「另一个页面正在应用」的假提示条。状态文件只在**确实 busy 时**用来展示上一步的页面名。
4. **子进程不能继承 fd 9**：调用 `ndsctl`、`/etc/init.d/opennds restart` 这类会 fork
   的命令时加 `9>&-`，否则子进程活着，锁就一直不放。
5. **只读接口不持锁**：`status` / `clients` / `client_detail` / 门户列表等都不走第 1 条那套
   "抢到才干活"的流程，否则界面上看个数据都要排队。唯一例外是 `status` 算 `busy`——
   按第 3 条「试抢即放」，`flock -n` 拿到就立刻 `flock -u` 放开，不写配置、不持锁到请求结束。
6. **纯缓存写也不加锁**：`/etc/config/zone_detect` 是插件自己的暂存区，**没有任何运行时读取者**
   （openNDS 与分发脚本都不读它，见《区域识别.md》§5），所以区域识别页的 `save_cache`、
   会话页的 `save` 不抢这把锁。它们只 `uci set` 自己那几个键，撞上别的页面正在 apply
   也改不坏对方的配置；反倒是 apply 那 15 秒轮询期间把「保存」变成"请稍候重试"纯属负收益。
   两个标签页同时保存同一面板，最坏是少写一条（重新点一次保存即可），不值得为它加锁。
   既要写 `zone_detect` **又**要写正式配置的接口（各页 `apply`）照常抢锁。

前端收到 `busy:1` 时：

- **不进入遮罩锁定态**（这次什么都没做，写进去的几率是零）；
- toast（warn）固定文案：「**等待上一步完成，请稍候重试**」；
- 页面顶部可显示一条提示条「另一个页面正在应用，请等待上一步完成」（`status` 里带 `busy:1` 时显示），
  按钮保持可点——点了再收到 busy 也是一样的提示；
- **不做自动重试**：两个页面互相重试会来回顶，交给用户手动再点。

适用范围：区域识别、OpenNDS 设置、客户端会话管理、路由器访问、WalledGarden、客户端豁免管理、
客户端黑名单、概览页的**落盘 / 重启类**写操作（含 `client_action`、`client_edit`、启停、重启）；
纯缓存保存按第 6 条不加锁。

### 11.4 `ndsctl` 调用约定（MAC 大小写 / 失败处理）

`ndsctl` 的 MAC 参数大小写不能想当然，各页统一按下面四条处理：

1. **uci 里存小写**：`preemptivemac` 条目、`trustedmac` 条目、`zone_blacklist.main.mac` 条目**全部小写冒号分隔**。`preemptivemac` 是小写的硬要求（见下）；另外两个为口径统一，更重要的是 `zone_blacklist` 有黑名单页与概览页两个写入方，大小写不一致会把同一个 MAC 当成两条，删除/判重全部失效。界面要显示大写就在渲染层转，别改存盘值。
   为什么 `preemptivemac` 必须小写：`libopennds.sh` 的 `preemptivemac()`
   把 `mac=` 的值交给 `dhcp_check`，后者用 `grep -w "$mac" /tmp/dhcp.leases` 比租约；
   dnsmasq 写的租约是小写，写成大写 → 这道检查永远不过 → `continue` → **该客户端永远进不了
   预认证队列**。`trustedmac` 没有这个依赖，但为口径一致也存小写。
2. **调 `ndsctl` 时大小写各试一次**：主进程客户端表的 key 由 nft / arp 侧生成，和 DHCP 租约
   不一定同格式。`ndsctl trust` / `untrust` / `deauth` / `auth` 先用小写，失败再转大写
   重试一次，两次都失败才记日志。少了这步的典型症状是「名单改了、界面提示成功、客户端还在线」。
   （`ndsctl` 的子命令随版本不同：10.x 是 `status` / `json` / `stop` / `auth` / `deauth` /
   `trust` / `untrust` / `debuglevel` / `b64encode` / `b64decode`；9.x 另有
   `block` / `unblock` / `allow` / `unallow`，但那些只在内存名单 + 现场插 nft 规则，
   重启即失效、也不换门户，不是持久黑名单，不要拿它顶 `zone_blacklist`。任何版本都
   **没有 `preauth`**——插件里的"免认证"是写 `preemptivemac`，不是调 `ndsctl`。）
3. **逐个执行、失败不中断**：批量处理多个 MAC 时单条失败不能 return。客户端不在线、
   或状态本来就是 `Trusted` 时 `deauth` 返回失败，属于正常现象。
4. **`ndsctl` 只做运行时动作**：它不写配置，重启即失效。要持久的一律落 uci，
   `ndsctl` 只是让改动立刻生效的加速手段——两者都要做，缺一个就是"界面改了实际没改"或
   "重启后又变回去"。

适用：豁免页 `save`、黑名单页「应用」、概览页行内操作（信任 / 免认证 / 解除认证 / 拉黑）。

## 12. 统一 JSON 返回信封（所有页面共用一个 `api()`）

后端是一个脚本、前端是一个 `api()` 包装函数，所以**只能有一种信封**。九页统一如下，页面文档里的示例字段名可以各写各的，但外层三个键不许变：

| 场景 | 返回 |
|---|---|
| 成功 | `{"ok":1, …业务字段…}` |
| 成功但需要提醒（预认证不生效、80 端口、关闭接管等） | `{"ok":1,"warnings":["…","…"], …业务字段…}`；前端逐条用 warn toast 展示。**是否同时显示成功 toast 由各页文档定**：「概览」的 preauth 无租约、WalledGarden/路由器访问的应用提醒，两种口径不同，按各自页面文档执行 |
| 业务失败（参数非法、校验不过） | `{"ok":0,"error":"…", …附加字段…}`；如 `{"ok":0,"errors":[{"line":3,"msg":"…"}]}`、`{"ok":0,"error":"duplicate","duplicates":[…]}` |
| 忙（抢不到锁） | `{"ok":0,"busy":1,"page":"<页面名>"}` |
| 环境/系统失败（缺工具、配置缺失） | `{"ok":0,"error":"…"}` |

规则：

1. **不再使用 `{"status":0|1}` 信封**——历史上概览/设置/区域/会话四页写过这一套，与其余四页的 `ok` 混在一起，前端必须两套解析，属于实现级冲突。统一以本节为准。
2. `ok` 是**唯一的成败判据**。`busy` / `duplicate` / `errors` / `warnings` 都是附加字段，不改 `ok` 的含义。`warnings` 恒定是**数组**（一条也写成单元素数组），前端不许按字符串解析。
3. **成败一律看 `ok`，不看退出码**。rpcd 的 `file.exec` 返回的是 `{code, stdout, stderr}`——非 0 退出码不会让调用失败，stdout 也照样回传（前端只解析 stdout）。为了避免"有的接口 `exit 1`、有的 `exit 0`"这种不一致，**业务失败（含 `busy`）也统一 `exit 0`**，错误只写在 `error` / `busy` 字段里；只有脚本自身起不来（缺 `flock`、解释器/依赖缺失）这类系统级问题才用非 0 退出码，并且**仍然输出一行 JSON**。
4. 纯文本日志一律走 stderr / `logger`，stdout **只允许**出现一行 JSON。
5. **参数一律按位置逐个传**：`file.exec` 的 `params` 是一个字符串数组，每个 `k=v` 是**一个独立元素**，
   后端按 `$1 $2 …` 顺序取。**不许**把多个参数用 `&` 拼成一个串（`"text_b64=…&passthrough=1"`）——
   那样后端得再做一层 URL 解码才能拆开，九页里只要有一页这么写，公共解析函数就得同时兼容两种格式。
   `confirm_enable=1`（§11.1）同样是"最后一个独立参数"。
   唯一不放进 argv 的是文件内容本身（走两段式上传，理由见《OpenNDS设置.md》§4.1；文本类内容走 base64 且限 64KB，见《路由器访问.md》§6.1）。

## 13. 页面文档与本文的从属关系

页面文档写业务，本文写跨页约定。两者冲突时的优先级：

1. 包名 / 路径 / 菜单 / ACL / 依赖 / 信封格式 → **以本文为准**；
2. 某个 uci 键由谁写、什么时候重启、锁怎么抢 → **以本文 §11 为准**；
3. 页面内的排版、文案、按钮可用性 → 以对应页面文档为准（版式来自该页演示 HTML）。
